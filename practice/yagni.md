# YAGNI 最小实现准则

目标不是“少写到草率”，而是：**在充分理解问题后，只构建当前真实需要的最小正确方案**。

## 优先级

1. **项目硬约束不可删减**：安全、数据不丢失、信任边界输入校验、桌面/进程隔离、数据库迁移安全、可观测性底线、用户明确要求的行为，不能被 YAGNI 简化掉。
2. **YAGNI 高于测试便利性**：不要为了“让测试好写”而提前增加生产抽象、wrapper、interface、DI 容器、factory、额外 seam 或配置项。
   - 如果某个测试必须依赖新增生产结构才能写，先停下来和用户确认：这是当前需求的真实架构问题，还是测试在逼迫代码变形。
   - 必要测试仍要保留，但优先测试已有公共接口和真实行为，不为测试伪造未被业务需要的层。
3. **YAGNI 高于深模块设计**：不要为了追求“架构更漂亮”而提前封装模块。
   - 只有当前需求、根因修复、可维护性阻塞或真实复用已经证明需要封装时，才引入模块边界。
   - 一旦确认需要模块封装，必须遵循深模块规则：小 interface、大 implementation、清晰 seam、高 locality、高 leverage。
4. **项目规范仍然适用**：文件命名、目录、语言栈、日志、数据库和测试工作流等，若仓库有项目约定则遵守。YAGNI 只约束“做多少”，不授权绕过那些约定。

## YAGNI 决策阶梯

对任何实现方案，按顺序停在第一个站得住的台阶：

1. **这件事真的需要存在吗？**
   - 推测性需求、未来可能、为了“扩展性”的空架子：不做。
   - 如果用户明确要求完整版本，才做完整版本。
2. **代码库里已经有了吗？**
   - 先搜索现有 helper、service、repo、hook、component、type、schema、测试 seam 和领域模式。
   - 不重写几份文件之外已经存在的能力。
3. **标准库能做吗？**
   - 时间、URL、集合、序列化、路径、stream、crypto 等优先用标准库。
4. **平台原生能力能做吗？**
   - HTML/CSS/浏览器能力优先于 JS 组件库。
   - 数据库约束优先于应用层重复校验。
   - 运行时原生机制优先于自建桥接。
5. **已安装依赖能做吗？**
   - 已有成熟依赖可直接复用。
   - 不为几行代码能解决的问题新增依赖。
6. **能否一行或小函数完成？**
   - 简单逻辑保持 inline 或提取为小的纯函数。
   - 不为一个调用点创建一层文件、一套 class 或一组 types。
7. **最后才写最小生产实现。**
   - 最少文件、最短正确 diff。
   - 只覆盖当前需求，不预埋未来。

## 明确禁止

- 单实现 interface。
- 单产品 factory。
- 只有一个调用方的纯转发 wrapper。
- 只为“以后可能变化”增加配置项。
- 只为测试 mock 方便而新增 production seam。
- 只为目录分层而保留一行转发函数。
- 重复造标准库、浏览器、运行时或已安装依赖已有的轮子。
- 在无真实需求时引入复杂状态机、插件系统、缓存层、队列、抽象 repository、manager/handler 大杂烩。
- 为解释一个简化方案写长篇防御性说明；如果说明比代码长，通常是复杂度从代码转移到了 prose。
- 以 YAGNI 为由省略安全隔离、错误处理、异步边界、迁移/备份或必要的日志上下文。

## Bugfix 规则：修根因，不修症状

Bug 报告描述的是症状。修改前必须理解真实调用链：

1. 找到用户可观察的失败。
2. 搜索即将修改函数 / 模块的所有调用方。
3. 优先在所有调用都会经过的共享位置修复。
4. 不要只在工单点名路径上补 guard，留下兄弟路径继续坏。
5. 如果根因位置没有合适测试 seam，先说明问题；不要为了测试便利随手新增生产抽象，需与用户确认。

懒惰修复不是最小表面补丁，而是**最小根因修复**。

## 测试与 YAGNI

测试用于证明当前行为，不用于驱动 speculative architecture。

- Bugfix 需要可复现检查；新行为需要与风险匹配的测试。
- 优先通过公共 interface / 已有 seam 测试外部行为。
- 不测试私有实现细节。
- 不 mock 自己的内部模块。
- 不为了 mock 方便新增生产 interface、adapter 或 DI 层。
- 如果没有正确 seam 能覆盖真实行为，先向用户说明并确认下一步：
  - 只做最小行为修复 + 手动验证；或
  - 将 seam / 模块边界调整纳入当前工作。

一句话：**测试必须服务于真实行为；生产代码不服务于测试幻觉。**

## 模块封装与深模块

YAGNI 默认拒绝新模块边界；但当当前需求、根因修复、测试 seam 或维护阻塞证明封装是必要的，必须遵循深模块规则。

详见 [deep-module.md](./deep-module.md)。

## 刻意简化的记录

如果为了当前交付刻意选择有上限的简化方案，必须标记清楚：

```ts
// yagni: process-wide lock is enough for single-user local runs; use per-resource locks if concurrent throughput becomes a real bottleneck
```

注释必须包含：

- 当前简化是什么。
- 它的上限是什么。
- 什么触发条件下升级。

没有触发条件的“以后再说”不是 YAGNI，是腐烂的技术债。

## 输出风格

实现时优先给代码和最短必要说明：

```text
已做 X。跳过 Y；当 Z 成为真实需求时再加。
```

复杂设计或用户要求解释时，可以完整说明；否则避免长篇方案游记。

## 最终判断

最好的方案通常是：

```text
充分理解问题 → 复用已有能力 → 遵守项目硬约束 → 写最小根因修复 / 最小当前功能 → 只在真实需要时设计深模块
```

YAGNI 的目标不是少负责，而是少制造未来必须负责的东西。
