# YAGNI

在理解真实调用链后，交付当前需求需要的最小正确方案。YAGNI 减少实现范围，不减少理解、正确性和项目硬约束。

## 决策顺序

按以下顺序选择，找到能够正确解决当前问题的最简单方案后停止：

1. **当前是否确实需要**：删除推测性需求和没有触发条件的未来扩展。
2. **仓库是否已有**：搜索现有模块、类型、组件、工具和测试入口。
3. **标准库是否支持**：优先使用语言与运行时提供的能力。
4. **平台是否原生支持**：优先使用浏览器、数据库、操作系统和框架的原生机制。
5. **已安装依赖是否支持**：复用成熟依赖；几行简单代码不新增依赖。
6. **小函数是否足够**：一个调用点的简单逻辑保持 inline 或使用局部纯函数。
7. **最后才新增业务代码**：使用最少文件和最小且正确的改动范围。

成熟库、标准能力和已有模块的判断基于正确性、维护成本和边界情况，不以行数作为唯一标准。

## 不可简化

安全隔离、信任边界输入校验、防止数据丢失的错误处理、数据库迁移与备份、必须异步处理的 I/O、网络或进程交互、必要日志、无障碍基础和用户明确要求的行为必须保留。

项目的命名、目录、测试、日志和技术栈规范仍然适用。

## 模块与测试

- 仅为假想的第二种实现新增公共接口或工厂，通常没有必要；隔离真实外部依赖不受此限制。只服务一个调用方的转发层和未使用的配置项通常也不应新增。
- 不为目录分层保留没有业务语义的一行转发。
- 测试优先通过已有公共接口验证真实行为。
- 不为方便 Mock 而在业务代码中增加公共接口、适配器、依赖注入容器或配置。
- 当前风险无法通过已有入口验证时，说明缺口；新增模块边界或测试入口前与用户确认它属于当前范围。

当前问题确实需要稳定公共能力、多个调用方共享决策或隔离外部系统时，再使用 [deep-module.md](deep-module.md) 设计边界。

## 缺陷修复

缺陷报告描述的是用户症状。修改前追踪相关函数的所有调用方，找到所有失败路径共同经过的根因。最小修复是在根因处改一次，而不是只在工单点名的调用方增加特殊分支。

缺陷修复至少需要一项能够复现原症状的验证；没有合适的自动化入口时说明人工验证和剩余风险。

## 刻意简化

有明确上限的简化方案使用注释记录：

```ts
// yagni: process-wide lock supports current single-user runs; use per-resource locks when concurrent throughput is required
```

注释应说明当前限制和重新评估的可观察触发条件。没有触发条件的“以后再做”不构成可维护的简化方案。

## 完成条件

- 当前需求已完整实现，未来需求没有提前实现。
- 已检查仓库、标准库、平台能力和现有依赖。
- 没有仅为测试或目录结构新增公共接口、适配器或转发层。
- 安全、数据、迁移、日志和用户明确要求未被删减。
- 缺陷在所有失败路径共同经过的根因处修复，相关调用方已检查。
