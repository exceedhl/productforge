# 日志与可观测性最佳实践

## 结构化日志

- **结构化输出**：生产环境日志应输出为一致的结构化格式（如 JSON），以便日志系统高效检索、聚合和告警。
- **开发环境可读性**：本地开发环境可配置 pretty-print，将结构化日志转成人类可读格式，但不得改变生产日志的机器可读性。
- **避免 `console.log` 散落**：应用代码应使用统一日志库和封装，避免在业务逻辑中散落无结构、不可检索的 `console.log`。

## 上下文与关联

- **无上下文不日志**：拒绝孤立日志点。请求日志必须关联 request id / trace id；非请求上下文应记录可定位的任务、会话、连接或组件标识。
- **不要为了凑字段而编造标识**：用户、会话、资源 id 只在真实存在且对排查有用时才写入。没有就省略，不要填 `"unknown"`、随机 UUID 或占位字符串——这类几乎不重复的值会把日志检索维度撑爆（这就是「高基数字段」），伪造的还会让检索对不上真实请求。

## 日志级别

- **DEBUG**：仅限本地和测试排查，生产环境默认关闭或严格采样。
- **INFO**：系统正常流转的里程碑事件，避免在循环或高频路径中滥用。
- **WARN**：系统出现异常但可自我恢复，例如降级、重试、跳过非关键任务。
- **ERROR**：导致请求、任务或用户流程失败的问题，必须携带足够的错误上下文和 stack trace，并可触发监控告警。

## 安全与脱敏

- **严格脱敏**：日志写入前必须对密码、Token、手机号、邮箱、身份证号等敏感信息和 PII 进行脱敏或过滤。
- **最小化记录**：默认不记录完整请求体、Cookie、Authorization header、密钥、原始文件内容等高风险数据；确需记录时必须采样、截断并脱敏。

## HTTP 日志

- **精简 HTTP 日志**：API 访问日志应剔除冗长或敏感的 Headers、Cookie 和无关字段，确保单次请求日志短小、可检索、可关联。
