# 数据库与迁移最佳实践

## 迁移管理

- **同频提交与目录隔离**：数据库迁移文件夹必须独立（如 `db/migrations`），但必须和业务代码存放在同一个仓库中。任何依赖新字段或新约束的代码变更，必须与对应的迁移脚本同步提交。
- **纯数字版本化与历史不可变**：Schema 和生产数据迁移文件必须使用严格递增的纯数字序列作为版本号前缀（例如 `001_init.sql`、`002_add_email.sql`）。一旦合并至主分支，旧迁移脚本不可变，任何修复必须通过新增版本文件解决。
- **测试与生产数据隔离**：迁移脚本仅限用于表结构变更和必要的生产字典数据。禁止在迁移脚本中插入测试数据；mock / seed 数据必须放在独立目录中。

## 用户数据安全

- **迁移前备份**：针对本地持久化数据库或用户自持有数据，执行破坏性或不可逆迁移前必须自动备份当前数据库文件，确保迁移失败时可回滚。
- **迁移失败可恢复**：迁移流程必须能明确报告失败原因，并避免留下半迁移、不可识别或无法再次迁移的数据库状态。

## 结构化数据字段

- **JSON 字段需要代码层升级器**：对于数据库中存储为 Stringified JSON 的字段，如果发生数据结构变更（例如属性更名、层级加深），仅靠 SQL Migration 通常无法完整处理。必须在代码层面提供 schema 升级 / 降级或兼容读取逻辑，在读取旧数据时自动转换。
