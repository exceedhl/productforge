# 设计规则

本文件用于判断模块职责、依赖方向和技术选择。先用 [yagni.md](yagni.md) 判断当前需要实现多少；确实需要抽出新模块时，再用 [deep-module.md](deep-module.md) 设计公共接口和内部实现。

## 优先复用成熟能力

实现新能力前按顺序检查：

1. 仓库中已有的模块、组件、类型和工具。
2. 语言标准库与运行平台的原生能力。
3. 项目已经安装的成熟依赖。
4. 业界成熟且维护活跃的依赖。

选择依赖时比较正确性、边界情况、维护状态、体积、安全和团队维护成本。成熟依赖能可靠解决复杂问题时，不重复实现解析器、状态管理、协议客户端或基础算法；几行简单代码足够时，也不为缩短代码而新增依赖。

## 按业务职责组织代码

- 代码优先按业务功能或领域聚合，使完成一项用户行为所需的规则集中在一起。
- 每个模块只承担一项可以用一句话说明的职责。
- 入口只负责组装和启动，不承载业务规则。
- 新分层必须隐藏复杂度或隔离真实依赖；只有转发作用的层应删除或合并。

## 明确各层职责

项目采用路由、Controller、Service、Repository 等分层时：

- 路由匹配协议入口并把请求交给 Controller。
- Controller 解析和校验协议数据，调用业务能力并返回协议响应。
- Service 编排业务流程和领域决策。
- Repository 或 Store 负责持久化读写，不决定业务流程。

这些名称不是必须建立的层。简单功能可以合并职责，但业务规则不应散落在协议入口和持久化代码中。

前端通常负责交互状态、本地化和展示；后端返回业务状态、错误码和结构化数据。采用服务端驱动界面等不同架构时，以项目明确约定为准。

## 隔离外部系统

领域逻辑不直接依赖数据库驱动、文件系统、网络客户端、LLM、操作系统或桌面运行时。把这些交互放在明确的基础设施实现中，通过领域需要的输入和输出与业务模块协作。

只有存在真实实现差异或需要在运行环境与测试环境中替换外部系统时，才增加依赖接口和适配器。

## 隔离旧版兼容代码

- 主业务流程只保留一条明确的读写路径，不在各层散布旧版条件分支。
- 旧格式读取、数据转换和迁移集中放置，只由迁移流程调用。
- 每条兼容路径说明停止支持的条件，避免新旧实现长期并行。

具体迁移目录、支持版本和下线条件由项目规则规定。

## 调整代码前先看完整调用链

合并、抽取或移动逻辑前，列出所有调用方并确认：

- 哪一层负责流程编排。
- 哪一层执行数据读写或外部请求。
- 哪一层作出领域决策。
- 相似代码是否处理相同场景和相同约束。

只有职责和变化原因相同的逻辑才合并。函数名称相似但业务场景不同，只统一必要的命名，不强行共享实现。

## 完成条件

- 新增代码没有重复现有能力或成熟基础能力。
- 模块按业务职责组织，依赖方向清楚。
- 协议、业务决策、持久化和外部系统各有明确归属。
- 新增层或接口隐藏了真实复杂度，不是纯转发。
- 旧版兼容代码与主业务流程隔离，并有停止支持的条件。
- 合并或抽取逻辑前已检查所有调用方。
