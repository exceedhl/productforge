# PRD

`/pf prd` 让用户画像、旅程、Story、PRD 和成功指标保持可追溯。

根据用户意图处理对应产物；只输入命令时，选择最先缺少且当前确实需要的产物：

```text
画像与旅程 → Backlog / Story → PRD → 成功指标与验证
```

设计与需求阶段先求质量：该写的画像、旅程、验收、范围和指标在编码前写清楚，不要为了缩短上下文而把完整 PRD 推迟到合并前。

## 开始前

读取已有的画像、旅程、Story，以及目标路径下已有的 PRD。只询问会改变产出的缺失决策，例如目标用户、要展开的 Story 或明确技术限制；仓库中已有答案时不重复提问。

事实、用户调研结论和产品假设必须区分。没有证据时写成待验证假设，不用具体但无来源的数字、心理描述或市场结论填空。

## 画像与旅程

聚焦当前决策需要的核心用户，而不是罗列所有可能人群。画像说明目标、场景、行为和阻碍；心理动机只有在有证据或明确作为假设时才写。

旅程按用户实际完成任务的阶段组织，不机械套用固定漏斗。每个阶段说明：

- 用户要完成什么。
- 通过什么触点采取什么行为。
- 遇到什么已知问题。
- 哪些产品改进值得验证。

使用 [template-journey.md](../templates/template-journey.md) 作为结构起点，并按项目实际删减。

## Backlog / Story

Story 必须能追溯到旅程中的问题或明确产品决策。每条 Story 包含：

- ID 和简要名称。
- “作为……我希望……从而……”形式的用户故事描述。
- 可观察的验收标准，覆盖主要成功路径和有代表性的失败场景。
- 依赖、范围和优先级。
- 当前实现需要的关键设计约束。

不要把没有用户价值的技术任务伪装成 Story；必要的技术工作作为 Story 的实施任务或明确的非功能需求记录。

## PRD

一个 Story 对应一个 `docs/prd/[ID]_[Brief].md`，使用 [template-prd.md](../templates/template-prd.md)。PRD 说明要解决的问题和可验收行为，不复制会快速过时的实现细节。

至少包含：

1. 问题、目标用户与使用场景。
2. In-Scope / Out-of-Scope。
3. 用户流程和关键状态。
4. 验收标准及 `Done`、`Partially Done`、`Pending` 状态。
5. 错误、权限、空态和关键边界条件。
6. 已确定的协议、数据或技术约束。
7. 成功指标和仍待决定的问题。

API 风格和数据模型遵守项目已有约定，不为形式统一另建协议或提前设计未来扩展。

## 成功指标与验证

指标必须对应当前产品假设和可取得的数据。优先确定一个能直接回答“功能是否解决问题”的主要指标；只有在有独立决策价值时才增加辅助指标和护栏指标。

需要实验时说明假设、实验组和对照组的条件、目标人群、观察周期、数据来源和判定标准。样本量或阈值没有数据依据时标记为待计算，不编造数字。

## 同步

上游变化后检查所有受影响的下游文档。只修改确实受影响的内容，并记录：

- 哪个假设或需求发生变化。
- 哪些 Story、验收标准或指标受到影响。
- 哪些代码和测试还需要同步或核对。

## 完成条件

- 每项需求能追溯到用户问题、旅程或明确的产品决策。
- 验收标准描述外部行为，可以据此设计测试。
- 假设与已验证事实分开。
- 范围、依赖和未决问题明确。
- 已检查下游 Story、PRD、架构和测试设计的一致性。
