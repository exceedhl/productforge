# 产品需求工程 (Product Requirements Engineering)

覆盖从用户研究到需求文档的完整链路：

```
用户画像 → 用户旅程地图 → Backlog/User Stories → PRD
```

`/lh prd`

用户说画像 / 旅程 / Backlog / Story / PRD / 成功指标 / 实验时做对应段；只点命令则按链路缺口推断。

## 模块导航

| 模块 | 输入 | 关键输出 |
|---|---|---|
| **用户画像 & 旅程** | 产品概念 | 画像 + 旅程地图表格 |
| **Backlog** | 用户旅程地图 | User Stories 表格 |
| **PRD** | User Story | PRD 文档 |
| **度量与验证** | PRD / 已上线功能 | 成功指标 + 实验设计 |

> 综合需求建议按链路顺序执行。
>
> **上游**: 建议先完成 `/lh strategy`。
>
> **下游**: Backlog 完成后，走 `/lh arch` 做架构设计。

## 交互式引导 (Interactive Discovery)

在开始任何模块之前，如果用户没有提供足够上下文，**必须先进行引导式提问**：

### 用户画像 & 旅程模块
1. **产品概述**: 用一句话描述你的产品解决什么问题？
2. **目标用户**: 你想聚焦的核心用户群是谁？（年龄段、职业、场景）
3. **现有认知**: 你对用户已经有哪些了解？（已有调研数据？还是纯假设？）
4. **产品阶段**: MVP 还是已有用户？有数据可参考吗？

### Backlog 模块
1. **旅程来源**: 是否已有用户旅程地图？文件路径是什么？
2. **开发约束**: 有多少开发资源？预计多少个 Sprint？
3. **优先级偏好**: 更关注用户增长、留存还是变现？

### PRD 模块
1. **Story 来源**: 从 `docs/user_stories.md` 中选择要展开的 Story ID
2. **技术约束**: 是否有特殊的技术限制或已定的技术选型？

> 收到足够信息后再执行。不要在信息不足时输出空泛的内容。

## 模块一：用户画像与旅程地图

### 核心原则
*   **单点突破**: 聚焦最典型的**单核心画像**。
*   **心理深度**: 深入挖掘心理状态、焦虑根源、价值观冲突。
*   **感官丰富度**: 包含具体场景感和感官细节，拒绝干瘪描述。

### 执行步骤

#### 第一步：核心画像 (Core Persona)
输出维度：基本面、心理侧写（焦虑/痛点、矛盾点、行为特征）。

#### 第二步：旅程地图 (Journey Map)
> 模板参见 `templates/TEMPLATE_JOURNEY.md`。

**阶段划分**: 因地制宜，拒绝生搬 AARRR。

**表格列**: 用户行为与触点（含感官细节）、用户目标 (JTBD)、痛点与挣扎、机会与解决方案。

---

## 模块二：Backlog / User Stories

### 核心原则
*   **源于旅程**: 所有 Story 必须追溯到旅程地图，严禁凭空捏造。
*   **可验收性**: 每个 Story 必须有清晰的验收标准。
*   **设计细节**: 包含关键设计点。

### 执行步骤

#### 第一步：解析旅程地图
按阶段提取核心功能点。

#### 第二步：编写 User Stories
表格列：ID、简介、User Story（"作为...我想...以便..."）、验收标准（3-5条，含异常流程）、关键设计点、依赖/阻塞、优先级 (P0/P1/P2)、技术落地计划。

### 分组结构
可按旅程阶段或实现顺序分组。

---

## 模块三：PRD 文档编写

> 输出模板参见 `templates/TEMPLATE_PRD.md`。

### 全局规则
- **One Story One File**: 文件名 `[ID]_[Brief].md`，存放在 `docs/prd/`
- **中文正文**: 仅文件名、ID、代码变量保留英文
- **验收标准含 Status 列**: Done / Partially Done / Pending
- **技术可行性**: 数据模型优先规范化，避免无理由反范式。API 风格与项目已有约定一致（HTTP、RPC、WebSocket、Agent tool 等均可），不要为了「看起来标准」另开一套协议。
- **YAGNI**: 严格区分 In-Scope 和 Out-of-Scope

## 模块四：度量与验证 (Measure & Validate)

### 适用时机
- 编写 PRD 时定义成功指标
- 功能上线后设计验证实验
- 需要决定是否继续投入还是 pivot

### 成功指标设计 (Success Metrics)

每个功能/Story 必须定义三类指标：

| 指标类型 | 说明 | 示例 |
|---|---|---|
| **主要指标 (Primary)** | 直接衡量功能是否成功 | 注册转化率提升 15% |
| **次要指标 (Secondary)** | 间接支撑主要指标 | DAU 增长、Session 时长 |
| **护栏指标 (Guardrail)** | 不能因为优化主要指标而恶化 | 跳出率不超过 X%、报错率不升 |

### 实验设计 (Experiment Design)

当需要验证假设时，设计如下：

```markdown
## 实验: [实验名称]
- **假设**: 如果 [做X]，那么 [指标Y] 会 [变化Z]
- **实验组**: [描述]
- **对照组**: [描述]
- **样本量**: [最小有效样本]
- **持续时间**: [天数]
- **主要指标**: [衡量什么]
- **判定标准**: [什么情况下算成功]
```

### 仪表盘需求 (Dashboard Requirements)

上线功能后，需定义需要追踪的数据：
- **实时监控**: 哪些指标需要实时告警？（如：错误率 > 5%）
- **日报/周报**: 哪些指标需要定期回顾？（如：转化漏斗）
- **数据来源**: 各指标的埋点方案或数据表来源
