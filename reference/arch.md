# 技术架构

`/lh arch` 记录技术取舍。根据用户意图处理系统架构或部署环境；两者可以独立执行。

- **系统架构**：模块职责、数据、协议、关键组件和 ADR。
- **部署环境**：运行拓扑、CI/CD、配置、密钥和其他敏感信息、回滚和本地开发。

只输入命令时，根据 Story、PRD 和现有文档选择当前实现所需的部分，不默认生成完整架构手册。

## 开始前

读取相关 Story、PRD、现有架构、ADR 和代码。只询问会改变方案的缺失约束，例如规模、安全、合规、目标平台或团队的技术维护能力。

先检查代码库、标准库、平台能力和已安装依赖。实现范围遵守 [yagni.md](../practice/yagni.md)；当前问题确实需要抽出新模块时再读取 [deep-module.md](../practice/deep-module.md)。

## 系统架构

围绕一条真实用户路径说明：

1. 用户或外部调用方从哪里进入。
2. 哪个模块负责业务编排和领域决策。
3. 数据在哪里读取、写入和迁移。
4. 哪些外部系统参与，失败时返回什么错误以及如何处理。
5. 前端如何获得并展示业务状态。

模块第一次出现时先说明职责。图只用于帮助理解关系；简单流程使用编号步骤即可。

只展开当前实现需要决定的部分：

- **技术选择**：候选方案、当前约束、取舍和选择结果。
- **模块与接口**：职责、依赖方向、输入、输出和错误返回方式。
- **数据**：实体、所有权、生命周期、一致性和迁移。
- **协议**：关键请求、响应、错误码和兼容要求；简单 CRUD 不逐项展开。
- **前端数据与状态**：哪个页面使用、用户操作后状态如何变化、数据来自哪里。
- **非功能要求**：将可验收的性能、安全、可靠性和可观测性要求写入 Story 或 PRD；纯实施任务保留为技术任务。

## ADR

只有同时满足以下条件时才创建 ADR：

1. 日后更改该决定的成本很高。
2. 没有上下文的维护者会质疑该选择。
3. 存在真实备选方案和取舍。

使用 [template-adr.md](../templates/template-adr.md)，记录背景、决策、备选方案、后果和状态。项目规定的 ADR 目录优先。

## 部署与环境

只记录运行和维护当前系统需要的信息：

- 环境与部署拓扑。
- 构建、发布、迁移和回滚顺序。
- CI/CD 的触发条件和交付检查。
- 环境变量、配置加载优先级，以及密钥和其他敏感信息的管理方式；不记录任何敏感值。
- Docker、Kubernetes、Terraform 等已采用的基础设施工具如何组织和使用。
- 本地开发的前置依赖、最短启动步骤和常见失败。

部署方案必须可复现，并明确开发、测试和生产差异。

## 同步

实现或设计变化后检查：

- 数据结构变化是否包含迁移、备份和回滚。
- 协议变化是否更新调用方和 API 文档。
- 新配置是否更新本地开发指南与部署说明。
- 重大取舍是否需要 ADR。
- PRD 验收标准和测试设计是否仍与方案一致。

## 完成条件

- 方案解决当前 Story，不包含没有触发条件的未来扩展。
- 关键调用路径、数据所有权，以及失败时如何返回和处理错误均已说明。
- 每项重要选择都有约束、备选方案和取舍。
- 新模块通过公共接口隐藏了真实复杂度，而不是增加转发层。
- 部署相关变更可复现、可回滚且不泄露敏感配置。
- 已检查 PRD、架构、ADR、测试设计和实现的一致性。
