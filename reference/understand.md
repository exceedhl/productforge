# 代码导览

`/lh understand` 为现有代码或改动生成结构化导览，解释整体架构、入口、调用、数据和测试。仅在用户明确调用，或明确要求代码导览、架构 / 时序可视化、当前结构或改动讲解时进入。

单个符号问题、故障诊断、实现、未来设计和代码评审不触发本工作流。`understand` 不评判严重度、不设计未来架构，也不修改生产代码。

## 1. 选择范围与视图

范围和视图是两个独立选择。先确定讲哪里，再确定展示当前状态还是变化。

### 范围

- **改动集**：工作区 diff、分支、提交区间或 PR 中发生变化的代码及必要上下文。
- **指定区域**：用户点名的 Story、用户路径、System、Container、Component、Module、Unit、目录或文件。
- **整体仓库**：整个 repo 的 System、Runtime Container、核心 Component、Store、外部 System 和少量关键路径。

没有范围时询问用户选择「当前改动」「指定区域」或「整体仓库」，不自动选择工作区 diff。用户说「整体」「全局架构」或「整个 repo」时直接使用整体仓库。

### 视图

- **当前视图**：展示所选范围现在的结构、路径和测试。
- **变化视图**：比较明确基线与当前结果，展示增加、删除、修改、移动和依赖变化。

「现在怎么实现」「整体有哪些」「当前结构」使用当前视图；「改了什么」「变化」「对比」「diff」使用变化视图。仍然不明确且结果差异明显时再询问。

变化视图必须有基线：工作区通常比较 `HEAD` 与当前工作树；分支使用明确 base 或 merge-base；提交区间和 PR 使用指定 base。基线不明确时询问，不能改用当前视图。记录范围、两端和差异统计；没有差异时直接说明。

## 2. 追踪真实路径

当前视图以当前代码为准；变化视图分别确认基线和当前端的入口、调用、数据写入与可观察结果。沿一条主要用户路径从入口跟到最终的数据读写或外部请求：

1. 读取匹配的 Story、PRD 和设计文档，了解产品意图。
2. 读取页面入口或协议入口。
3. 顺序跟进编排、领域逻辑、持久化和最终的数据读写或外部请求。
4. 变化视图补读基线版本，区分原有上下文与本次变化。
5. 引用前读取对应端的当前文件。

文档与代码不一致时分别说明二者内容，不根据一方内容推断另一方未写明的事实。排除与所选范围无关的生成文件、历史报告和本工作流文件的改动，除非用户点名。

## 3. 面向未读过代码的人

内部术语第一次出现时先说明职责，再给标识符。先解释用户行为，再解释文件和调用关系。

描述模块协作时使用“集成”；项目测试层名使用 `Integration`。

## 4. 组织导览

按范围和复杂度选择以下模块，不为固定模板生成空章节：

1. **范围与视图**：范围、当前 / 变化视图；变化视图注明基线。
2. **简要结论**：用户侧行为或主要变化。
3. **架构结构**：需要时展示包含关系、分层、关键 Unit、Contract 和依赖。
4. **用户路径**：用户从哪里进入、做什么、得到什么；必要时补充失败、空态和限制。
5. **运行顺序**：用调用链或时序图解释关键参数、副作用和结果。
6. **关键状态与数据来源**：只在存在持久化、缓存或派生数据时展示。
7. **变化摘要**：仅变化视图，分别说明架构、调用、状态和测试变化。
8. **测试结构**：测试属于当前范围且有理解价值时展示。
9. **关键实现规则**：列出 3–7 条不能误解的机制及代码位置。
10. **阅读入口**：指定区域保持精简；整体仓库按 Container / Component 分组推荐入口，不固定文件数量。

简单区域只需结论、调用说明和阅读入口。整体仓库优先给出全局架构图、2–4 条关键用户路径、核心 Store / 外部 System 和阅读入口，不逐文件复述。

## 5. 选择视觉形式

只使用能让当前重点更清楚的最小视觉：

- 规则或算法用简短伪代码。
- 简单调用顺序用 call tree；多参与方、并发或回调用时序图。
- 系统组成、代码包含、架构分层和关键静态依赖用架构结构图；不要用时序图承载静态结构。
- UI 组合关系用组件树，文件职责变化用浅层文件树。
- 重点是「改了什么」且上下文结构已知时用 diff；省略上下文会隐藏职责或顺序时展示完整结构。
- 内容密集、需要颜色或交互才能读清时生成一个聚焦的 HTML 文件并打开。

### 当前视图与变化视图

架构图、时序图和测试结构都支持当前视图与变化视图。当前视图不加 diff 标记；变化视图统一使用：

- `+ Added`：绿色外框或边条。
- `− Removed`：红色虚线外框并降低填充，不从图中直接消失。
- `~ Modified`：黄色外框或边条；在元素内并列最小必要的旧值 / 新值。
- `↔ Moved / Renamed`：蓝色标记，并用短连线或 `old → new` 说明身份 / 归属变化。
- `Context`：未变化但理解本次变化所必需的元素使用中性弱化样式。

状态必须同时显示符号和文字，不能只靠颜色。架构分层已经使用 Box 背景色，因此变化状态只使用外框、边条和状态 Badge，不覆盖分层颜色。

结构基本稳定时在单图叠加 diff；大范围移动、重命名、增删或调用重排时改用同尺度的 `Before` / `After`，保持相同位置、图例和缩放。

### 时序图的场景与 Lane

时序图默认展示主要成功路径；有重要分支时在图例标明场景，不把互斥路径串成一条调用链。

Lane 按用户路径的运行阶段和主导目标划分，例如「选择能力 → 修改文档 → 显示结果」，不按目录或技术层分组。每个调用只属于一个阶段；目标未变不另起 Lane，简单调用链省略 Lane。

Lane 与测试场景分类是两个维度：

- Lane 表示同一场景按时间推进的阶段；Happy path、Sad path 和 Boundary 表示从某个条件处分出的不同场景。
- 主要成功路径可作为主图；代表性异常路径在真实分叉点使用 `alt` / 分支区块，或拆成独立小图。不能把「Sad path」画成成功路径之后的下一阶段。
- 边界值沿用相同调用顺序时只标注触发条件，不新增 Lane；边界条件改变参与方、副作用或可观察结果时才画分支。
- 关键的用户可观察分支应能对应测试中的正常、异常或边界场景，但导览图不要求与每条 `it` 一一对应，也不展开与用户结果无关的输入组合。

### 架构可视化共享规范

#### 概念模型

代码包含关系统一使用以下层级：

```text
Software System
└── Runtime Container
    └── Architectural Component
        └── Language Module
            └── Unit
```

- **Software System**：提供完整产品能力的软件系统，例如 Vis、飞书。外部 SaaS 也属于 System。
- **Runtime Container**：可独立运行的应用、进程或前端应用，例如 Backend Node 进程、Frontend SPA、Desktop。这里的 Container 不专指 Docker。
- **Architectural Component**：Container 内围绕一项完整能力组织、具有明确公共入口并隐藏多个内部 Module / Unit 的架构边界。Component 是语言无关概念。
- **Language Module**：严格使用当前语言的定义，不能把普通目录或业务能力随意称为 Module。
- **Unit**：具有明确运行时身份和可调用行为的最小封装单元。TypeScript / Java 的对象或 class 实例、Rust 的 struct 实例都属于 Unit，不按语言语法拆成多种视觉类型。

Actor 和 Store 可直接作为参与方，但不属于代码包含链。React Component 只有承接入口、关键状态、副作用或用户可见结果时才作为 Unit。

Component 应具备内聚能力、明确入口、内部隐藏和相对独立演进。Plugin、Integration、Feature、Domain 仅在代码库确有该边界时使用；目录本身不能证明 Component 存在，也不显示含义模糊的「Group」。

#### 语言实现对照

- **TypeScript**：Component 常由目录或 package 加公共注册 / 导出入口实现；Language Module 是使用 `import` / `export` 的源文件；Unit 是对象或 class 实例。
- **Python**：Component 常由一个 package 或多个协作 package 实现；Language Module 是 `.py` 文件；Unit 是对象或 class 实例。
- **Java**：Component 可由 package 集合、Spring 组件边界或 JPMS module 实现；package 和 JPMS module 按项目真实结构分别命名；Unit 是 object / bean。
- **Rust**：Component 常由 crate 或内聚的顶层 module tree 实现；Language Module 是 `mod`；Unit 是 struct 实例。

这些不是强制映射；根据实际入口、注册和依赖边界判断 Component。

#### Contract 与架构分层

Interface、trait 和 protocol 统一称为 **Contract**。它是 Unit、Module 或 Component 遵循 / 提供的关系，用边界端口和名称表达；只有解释静态接口依赖时才独立成节点。

架构分层与包含关系正交。Controller、Service、Model、Repository、Gateway、Presentation 等回答「负责什么」，System、Container、Component、Module、Unit 回答「属于谁」。分层使用参与方 Box 的背景色表达；图例同时写出颜色对应的层名，不能只靠颜色传达。包含关系的背景框保持中性，不能与分层颜色混用。沿用仓库已有层名和职责；Repository 与 Service 同属一个 Component 时仍保持独立职责。

#### 展示颗粒度与包含关系

展示颗粒度由讲解目的决定。焦点区域可以展开到 Unit，上下文区域可以保留为 Component、Container 或 System；不要求全图同级。混合颗粒度时必须明确区分：

- 展开的 System、Container 或 Component 使用带名称的嵌套背景框，直接包住对应多列参与方；背景框没有生命线。
- 折叠的 System、Container、Component 或 Module 使用参与方 Box 和对应图标，并产生生命线。
- 只包住一个参与方、没有提供当前问题所需边界信息的背景框应省略。目录路径可以留在 Box 中，不据此编造边界。
- 同一容器中的参与方尽量相邻排列；外部上下文可以保持折叠，即使焦点区域已经展开到 Unit。

#### 参与方 Box

Box 主体只显示「类型图标 → 平实职责 → 代码身份」：

1. 类型图标区分 Actor、Unit、Language Module、Component、Container、System 和 Store；图例给出文字含义。
2. 平实职责是视觉主标题，代码身份使用等宽字形。文件名统一放在 Box 右下角 Badge 中并使用等宽字形，不与职责或代码身份形成等权正文；折叠的 Component / Container / System 没有单一文件时省略文件名 Badge。
3. Contract 使用 Box 边界上的端口图标和名称，不写成普通信息行。
4. 没有代码身份、文件名或 Contract 时省略对应内容，不补占位符，不虚构类名。普通参数和结果类型不作为参与方；一个参与方承载多个无关职责时拆图。

#### 示例：飞书文档主路径

```text
SYSTEM · Vis
└── CONTAINER · Backend
    └── COMPONENT · Feishu Integration
        ├── TS MODULE · registerFeishuIntegration.ts
        ├── TS MODULE · feishuFreeWrite.ts
        │   └── UNIT · integrationTool
        │       └── ○ IntegrationToolDefinition
        └── TS MODULE · docxApi.ts

EXTERNAL SYSTEM · Feishu OpenAPI
```

这里的 Feishu Integration 是 Architectural Component：它通过注册入口向 `IntegrationRegistry` 暴露完整飞书能力，并隐藏多个内部 TypeScript Module。Backend 是 Runtime Container，不标为 Software System；飞书 OpenAPI 属于外部 Software System。

### 架构结构图展示规范

架构结构图回答「系统由什么组成、代码属于哪里、处于哪一层、依赖指向哪里」，不替代时序图。

1. **选择焦点**：标题和图注写明范围。焦点 Component 展开到必要的 Language Module、Unit 和 Contract；上下文区域保留为折叠的 Component、Container 或外部 System。
2. **显示包含关系**：使用中性的嵌套背景框包住多列内容，依次表达 System、Container、Component 和必要的 Language Module。折叠节点使用普通 Box；只有一个子节点且对当前问题没有解释价值的背景框省略。
3. **突出关键 Unit**：对入口 / 出口、核心编排、关键决策、权威状态、持久化或外部网关、关键 Contract 实现使用较粗边框和 `KEY UNIT`。每张图通常只突出 5–8 个。
4. **显示静态关系**：实线表示直接依赖或调用，虚线表示事件、异步通知或结构化结果；访问 Store 时标明 `read` / `write`。方法只在定义关键依赖时标在线上。
5. **不照抄 UML**：不列完整字段、方法、可见性和继承细节；背景框已表达包含关系时，不再使用组合菱形。
6. **适合截图**：HTML 使用全宽、无固定侧栏的 16:9 附近画布；图例置顶，核心结构尽量在首屏完整出现，过宽时保持字号并横向滚动。

架构结构图与时序图应复用同一套 System / Container / Component / Module / Unit、Contract、分层颜色、文件 Badge 和代码命名，避免同一对象在两张图中出现不同身份。

#### 架构变化视图

架构变化图保留受影响节点的一层必要上下文，只突出本次改变的边界、Unit、Contract 和依赖：

- 新增 / 删除 System、Container、Component、Module、Unit 或 Contract 时，在原有位置显示 `+ Added` / `− Removed`；删除项保留为弱化虚线轮廓。
- 职责、代码身份、文件或架构层发生变化时使用 `~ Modified`，只显示变化字段的 `old → new`，其余 Box 信息保持当前值。
- 节点在包含树中移动或重命名时使用 `↔ Moved / Renamed`；小范围变化可在单图用旧位置虚影和迁移连线，大范围变化使用 Before / After。
- 新增依赖使用带 `+` 的绿色实线，删除依赖使用带 `−` 的红色虚线，调用方向或关系种类变化使用 `~` 并标明旧 / 新关系。
- Component 内部实现变化但公共 Contract 和外部依赖不变时，不把整个 Component 标成修改；只标记实际变化的 Module / Unit。

整体仓库的架构变化视图仍以受影响区域为焦点，在旁边保留未变化的 Container / 外部 System 作为定位上下文，不能把整个 repo 的所有节点都染成 diff。

### 时序图的消息与排版

#### 箭头上的消息

1. 每条消息按「动作概括 → 方法 → 关键参数本义」显示，并与对应箭头组成一个视觉单元。
2. 动作概括说明这一步为什么发生；方法名使用代码样式；参数说明只保留影响目标、身份、权限、位置或副作用的字段，并用平实文字解释用途。例如：`connectionId` 指向当前用户的 OAuth 连接。
3. 函数和方法默认属于箭头消息；不展示完整函数签名，不重复顶部已有的代码身份，不把动作、方法和参数压成一串等权文字。
4. 返回箭头使用较弱样式，先说明结果用途，再列调用方后续会使用的关键字段及含义；不复述完整响应对象。

#### 时序变化视图

- 参与方和 Lane 稳定时保留一张时序图：新增调用在线上标 `+ Added`，删除调用保留红色虚线并标 `− Removed`，修改调用标 `~ Modified`。
- 动作、方法或关键参数变化时，在同一消息标签中只显示变化部分的 `old → new`；没有变化的动作说明和参数不重复。
- 新增 / 删除参与方、调用顺序明显改变、调用跨 Lane 移动或 Happy / Sad 分支结构变化时使用 Before / After 双图，不用交叉箭头强行叠加。
- Lane 名称或阶段归属变化属于用户路径变化，使用 `↔ Moved` 标出旧阶段与新阶段；仅内部方法变化但用户阶段不变时不修改 Lane。
- 返回字段或可观察结果变化标在返回箭头上；只有内部中间值变化且调用方不使用时不进入主图。
- 未变化的调用链使用中性弱化样式作为上下文；从入口到变化点、再到用户可见结果必须保持可追踪。

#### 整体排版

- 中性的嵌套背景框表达展开的 System / Container / Component 包含关系；参与方 Box 背景色表达架构分层，并在图例标注层名；Contract 端口表达接口关系。三者不能使用同一种视觉形式。
- 顶部边界、参与方 Box、阶段标题、调用消息和返回消息形成稳定的视觉层次；相同类型使用一致图标、字号、字重、颜色和间距。
- 阶段标题紧贴对应区域左上角，消息说明放在箭头上方且不与生命线、箭头或相邻消息重叠。
- 优先让核心内容充分使用可用屏幕宽度。目录、图例和辅助导航价值较低时放到顶部、折叠或缩窄，不为固定侧栏长期预留大块宽度；时序图、结构图和数据密集区可以使用更宽的内容容器。
- 内容过宽时保持可读字号并允许横向滚动，不为了塞进一屏缩小到难以阅读。

视觉紧邻它所支持的说明，只保留理解当前问题需要的调用、文件、状态和边界。使用真实名称与数据，不为了展示形式增加无关内容。

## 6. 选择输出载体

导览支持两种输出载体：

- **对话**：适合简单的指定区域、单条调用链和短 diff 说明，默认使用。
- **HTML**：适合用户明确要求 HTML、整体仓库范围、架构 / 时序变化图，或完整导览包含多个入口、调用路径、状态和文件关系。

用户明确选择时按其要求。整体仓库默认生成全宽 HTML；变化较多时使用状态图例、叠加 diff 或 Before / After。HTML 使用顶部紧凑导航、必要的折叠和颜色，并保留代码路径与行号；对话只给摘要和文件位置。

HTML 是本次讲解的本地可视化产物，不等同于 Walkthrough 文档，不默认提交。用户要求持久化文档时仍按「写入文档」处理。

## 7. 理解测试

测试沿用全局两种视图：

- **当前视图**：展示所选测试范围现在的完整结构。
- **变化视图**：回答基线与当前端之间哪些测试增加、删除或修改。

两种视图都优先按测试文件分组，并列出主要被测生产文件和类、函数或公共方法。Integration / Journey 没有单一方法时，标注被测入口或用户流程，不虚构代码符号。

### 测试变化视图

使用 `+` / `-` 展示变化，每条 `it` 标注主要分类。

```diff
backend/tests/unit/report/reportDsl.test.ts
  被测对象：backend/modules/report/reportDsl.ts · resolveReportDsl()
- describe('Report 测试')
+ describe('resolveReportDsl 版本读取')
-   it('旧字段不会被回填') 〔已删除逻辑〕
+   it('当前版本数据解析成功') 〔Happy path〕
+   it('缺少 version 时按 v1 升级') 〔边界：缺失版本〕
+   it('缺少必填字段时返回 fallback') 〔Sad path：输入校验〕
```

diff 中未列出的用例表示保持不变。测试文件移动或 `describe` 重组使用 `↔ Moved / Renamed` 标记；只有标题变化但行为未变时不能写成新增 / 删除用例。

### 测试当前视图

生成一个聚焦的 HTML 文件并为用户打开，不在对话中堆叠完整用例列表。HTML 保持测试文件的真实层级：

1. 页首显示测试文件、用例总数和各分类数量。
2. 测试文件下列出主要被测对象。
3. 每个 `describe` 使用独立区块；`it` 以紧凑行嵌套在对应 `describe` 下，并按源码顺序排列，不为每条用例创建独立大卡片。
4. Happy path 使用绿色，Sad path 使用红色，边界使用黄色，回归使用紫色，护栏使用蓝色；同时显示文字标签，不能只靠颜色传达含义。
5. `describe` 与 `it` 标题使用清晰的字号和字重区分；用例较多时允许折叠 `describe`。
6. 使用真实名称和当前数据，支持桌面与移动端；不添加与理解测试无关的装饰、图表或说明。

指定区域必须包含范围内全部 `describe` / `it`。整体仓库先按包、测试层和 Component 展示测试拓扑与数量，用户明确要求时才展开全仓用例。每个用例只选一个最能说明存在价值的分类，不堆叠标签。

两种视图都只说明结构、分类和必要上下文，不逐条复述 `it` 标题。

## 写入文档

本地 HTML 可视化不算持久化文档。用户明确要求写入文档时使用：

```text
docs/design/[ID]_Walkthrough.md
```

没有 Story ID 时使用短 slug。已有文件继续修改。文档包含 `last_updated`、`status: Draft`，有关联 Story 时包含 `related_stories`。

## 完成条件

- 范围与视图明确；变化视图记录了基线和当前端，整体仓库视图给出了全局架构而不是文件清单。
- 用户可以说清功能从哪个入口开始，最终读取或写入什么。
- 关键参与方的归属和调用关系清楚，内部名称第一次出现时有职责说明。
- 架构图、时序图和测试展示使用一致的当前 / 变化语义；变化元素与必要上下文可以区分。
- 代码与文档差异已明确标出。
- 引用来自当前文件并可定位。
- 没有混入严重度、Decision Board 或未经请求的未来设计。
