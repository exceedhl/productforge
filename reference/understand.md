# 代码导览

`/lh understand` 解释已经存在的代码，帮助未读过这批改动的人理解功能入口、调用顺序和数据变化。它不评判严重度、不设计未来架构，也不修改代码。

## 1. 确定对象

优先使用用户指定的 Story、路径、分支或工作区。未指定时，先看当前工作区的代码差异；没有改动再看当前分支相对 `origin/main` 的差异。

记录变更路径、差异统计和相关提交。没有代码差异时说明没有可讲解的对象，不根据文档猜测实现。

## 2. 追踪真实路径

以当前代码为准，沿一条主要用户路径从入口跟到最终的数据读写或外部请求：

1. 读取匹配的 Story、PRD 和设计文档，了解产品意图。
2. 读取页面入口或协议入口。
3. 顺序跟进编排、领域逻辑、持久化和最终的数据读写或外部请求。
4. 引用前读取当前文件。

文档与代码不一致时分别说明二者内容，不根据一方内容推断另一方未写明的事实。排除与主路径无关的生成文件、历史报告和本工作流文件的改动，除非用户点名。

## 3. 面向未读过代码的人

组件、函数、类型、ADR 或内部术语第一次出现时，先说明它实际负责什么，再给标识符。先解释用户做了什么，再解释文件和调用关系。

描述模块协作时使用“集成”；项目测试层名使用 `Integration`。

## 4. 组织导览

按改动复杂度选择必要内容，不为了固定格式增加空章节：

1. **简要结论**：用户侧发生了什么，哪份数据是权威来源，哪份是派生副本。
2. **用户路径**：用户从哪里进入、做什么、得到什么；有重要空态、限制或错误处理路径时一并说明。
3. **调用顺序**：用编号步骤或 Mermaid 时序图解释谁调用谁、传入什么、最终写入或返回什么。
4. **分层关系**：跨越多个层或容易误读时，用图和简短说明解释每层负责什么、不依赖什么。
5. **关键状态**：只列理解流程必须知道的持久化字段或内存状态。
6. **关键实现规则**：列出 3–7 条读代码时不能误解的机制，并给出对应文件。
7. **阅读顺序**：最多 5 个文件，说明先后理由和可以暂时忽略的、与主流程无关的其他调用路径。

简单改动只需要简要结论、一条调用链说明和阅读入口。多入口、跨层或有持久化状态时再增加图、词表和分层说明。

## 写入文档

默认只在对话中输出。用户要求文档时写入：

```text
docs/design/[ID]_Walkthrough.md
```

没有 Story ID 时使用短 slug。已有文件继续修改。文档包含 `last_updated`、`status: Draft`，有关联 Story 时包含 `related_stories`。

## 完成条件

- 用户可以说清功能从哪个入口开始，最终读取或写入什么。
- 主要模块按调用顺序出现，每个内部名称第一次出现时都有职责说明。
- 代码与文档差异已明确标出。
- 引用来自当前文件并可定位。
- 没有混入严重度、Decision Board 或未经请求的未来设计。
