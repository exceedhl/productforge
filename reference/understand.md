# Understand

`/lh understand`

对着一批**已经存在的代码**（分支、工作区、Story）写阅读导览：用户怎么走、请求怎么串、层与实体怎么认、读代码先看哪。目标是人还没读过这批（常为 AI 生成）代码时，能尽快建立心智模型。

**不是** `/lh arch`（编码前写架构/ADR），也 **不是** `/lh review`（六轴评判该不该改）。本命令只讲解，不打分、不列 P0/P1、不改代码（用户另要求 fix / 落盘除外）。

## 何时使用

- `/lh understand`、`/lh understand US-093`、相对某基线 / 当前工作区
- 用户说：读懂这块、讲解改动、怎么走、分层关系、帮我尽快了解设计
- review 里 Brief 太像结论备忘、用户明确要「当没读过代码来讲」

## 总流程

### 1. 定对象

按序收窄，不要全仓扫：

1. 用户点名的 Story ID / 路径 / 「当前工作区」
2. 未指定：工作区脏 diff（`git diff HEAD` + untracked）；再空则相对 `origin/main` 的分支 diff
3. 校验 diff 非空。空 → 失败并说明，不要空讲

采集：变更路径、`git log`/`git diff --stat`。排除无关（skill 自身、上次 review 报告），除非用户要讲那些。

### 2. 读什么

**以当前代码为准。** 引用前必须 `Read` 文件。文档用来对照产品意图，不得只靠 PRD 臆造调用链。

有则读、没有就跳过并注明：

- 匹配的 PRD / Design / Story（`docs/prd/`、`docs/design/`、`docs/user_stories.md`）
- 关键生产文件：入口 UI、编排 Service、持久化、对外集成
- 一条主路径从点击跟到 IO（不要每个改动文件平铺）

代码与文档不一致：写「代码实际是…；文档写的是…」，不要默默按文档讲。

### 3. 读者模型（必须）

默认读者 **还没读过这批代码**。禁止第一句并列模块名；禁止把 ADR 编号、helper 名、管道名当已知。

第一次点名必须先说它干什么：

- 错：「出站走 `exportViaDestination`，AC-93.13 边界成立。」
- 对：「Dataset 把结果表 **写到** 飞书（出站，相对从飞书读进来）。中间不直接调飞书 SDK，只对通用导出函数说『目的地 + 这些行』。」

词表在分层之前。领域隐喻（入站/出站、绑定、管道）各一词一句。

## 产出结构（按序，缺段则重写）

对话正文必须自成一体。不要把六轴 Finding 揉进来。

### 1. 一句话

这批改动在用户侧加了 / 改了什么（5–8 句，**不提文件名、不提 AC 编号**）。真源是哪、副本是哪，一句话说清。

### 2. 用户会碰到的几条路

表格：**你想做什么 | 点哪里 | 结果**。含空态、限额、和「不要走这条」的入口（例如已绑定表不要再走导出）。没做的入口写「现在没有」。

### 3. 时序

主路径 1–2 条 mermaid `sequenceDiagram`（参与者用职责名 + 文件名）。每条图下用 2–4 句标出容易误读的点（例如：确认当下才开跑；成功后不再全量再写一遍；本地成功和远端成功是否分开）。

### 4. 分层：谁认识谁

一张 mermaid（谁调用谁）。再表：**实体 | 文件 | 它懂什么 | 它不懂什么**。箭头只往下；点名「哪一层不许 import 哪一层」时，用白话说清为什么，再括文档编号。

### 5. 关键状态记了什么

若有库表 / 关键内存对象：只列读代码必须盯的字段（一字段一句）。没有持久化则写「无落盘，状态在…」。

### 6. 实现要点

3–7 条 **读代码时的不变量**，不是 review 建议。每条：机制 + 对应文件。例如两种写模式不要合成一个函数、认领/协作列、装行用哪份筛选。

### 7. 建议阅读顺序

5 个以内文件，有顺序理由（先产品流程、再编排、再集成、再 UI）。点明「可以先忽略」的平行域（如方向相反的入站）。

## 落盘

默认 **只写对话**。用户说落盘 / 写成文档时：

```
docs/design/[ID]_Walkthrough.md
```

无 Story ID 则用短 slug。已有同路径则接着改。顶部 YAML：`last_updated`、`status: Draft`、有 Story 则 `related_stories`。本仓库架构文档在 `docs/design/`（见 `AGENTS.md`）；不要写到 `docs/adr/`。

## 禁止

- 当 review 用：不打严重度、不写 Decision Board、不建议立刻改（除非用户当场转成 review/fix）
- 当 arch 用：不新写 ADR、不扩未来模块
- 用「欠债 / 收口 / 边界成立 / SPI」代替「它实际做了哪一步」
- 全文件粘贴；导览里点名即可，细节让用户去 Read
- 把测试文件当主叙事（可在阅读顺序末尾提「对一下测设场景」）
