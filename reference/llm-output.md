# LLM 输出约定（通用）

适用于 **所有** `/lh` 子命令产出、对话回复、设计/测设/review 正文与提交说明。  
**不是** `/lh review` 的 Conventions 轴标准；Conventions 轴只评代码命名、目录、日志、迁移（见 [conventions.md](conventions.md)）。

---

## 用语

对用户说明、文档与代码注释一律用本义、标准术语。禁止黑话、口语比喻、自造隐喻。

- **技术用语用标准名**：协议、接口、凭证、错误用行业/官方用词（如 `access_token`、`refresh_token`、授权码 `code`、刷新、single-use、refresh token rotation）。没有通行译名时保留英文，不另起中文黑话。
- **禁止用「票」比喻凭证**：不写「票」「换票」「兑票」「一次性票据」。
- **禁止用「打」代替访问/请求**：不写「打飞书」「打接口」「打 token 接口」。写访问、请求、调用，或 `access` / `request`。
- 讨论技术内容比如测试和设计的时候禁止用“钉住”，“一刀”，“落点”这种词汇。
- **不要跳跃性回复**：先答所问，再按时间顺序或调用链顺序往下写。一步只推进一个环节；不要跳步、不要前后穿插互不相关的点。缺上下文时先补齐，不要默认读者已跟上未写出的中间步骤。
- **引用必须可定位**：凡引用代码、文档、日志、官方说明，必须给出读者能立刻点开或搜到的位置。代码用带路径与行号的引用块；仓库文档给相对路径（必要时加标题/节名）；外部资料给完整 URL。禁止无出处摘句、禁止只写「见上文」「如前所说」而不指回具体位置。

---

## 说明设计与实现

写「现在怎么工作 / 问题在哪」时，**不默认读者已读过代码**。对话、战略/PRD/架构/ADR、测设、review 报告、提交说明一律适用。最低要求：

1. **先交代场景**：哪个页面或入口、用户做什么、期望看到什么。
2. **按调用顺序写**：谁调用谁、传入什么、返回什么、下一层拿去干什么。一步只推进一个环节。
3. **名字第一次出现先解释**：组件、函数、类型、API 先用一句话写职责，再写标识符。不要只抛 `onLoadGroup`、`groupPath` 这类符号。
4. **两处相似逻辑要对照**：相同的是哪几步，不同的是哪一步（例如详情请求 Dataset browse，下钻请求 Widget drill 并多传图表点击点）。
5. **禁止压缩成黑话**：不写「表不发网」「打一枪」「unwrap」「契约适配层」「落点」「一刀」这类读者必须先懂代码才能解码的句子。改成本义，例如「表格组件不调用 HTTP API，由所在页面传入回调去请求」。
6. **关键步骤带可定位引用**：代码用路径 + 行号引用块；review 落盘用可点击的 `#L` 链接。

反例：「表不发网，只把 path 交给页面；两边都是当前查询 + groupPath → findGroupNodeByPath。」  
正例：先写表格用在详情页和下钻页、点开组头时表格只调用回调、两个页面各自请求哪条 API、接口仍返回整页所以还要从 `groups` 里取出一个组节点。
