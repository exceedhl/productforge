# 六轴评审

`/lh review` 基于固定的 Git 基线，对改动执行评审并将证据写入报告。该命令判断改动是否需要修改，不代替用户修改代码。

开始前读取：

- [review-axes.md](review-axes.md)：六轴标准、深度、跳过规则、子 agent 模型和判断重点。
- [review-format.md](review-format.md)：问题项、代码位置和报告格式。
- 仓库 `AGENTS.md`：项目规则优先。

## 1. 固定范围

先确定用户要评审分支改动还是仅评审工作区。分支评审使用用户指定的提交、分支、标签或其他 Git 引用；未指定且仓库没有明确默认时，询问一次，常见默认是 `origin/main`。用户明确只看未提交改动时，以 `HEAD` 为参照，不纳入当前分支已有提交。

「所有未提交」只表示**文件范围**是工作区，不表示要跑六轴。六轴只在第 3 节的全量深度启动。

开始评审前完成以下检查：

1. `git rev-parse <base>` 能解析基线。
2. 采集 `git log <base>..HEAD --oneline`、`git diff --stat` / `--name-status`、新增与删除行数、变更路径。
3. 分支评审默认包含 `<base>...HEAD` 的提交以及当前工作区已暂存、未暂存和未跟踪的文件；用户明确只看提交或只看工作区时按要求收窄。
4. 差异非空。基线无法解析或没有差异时在此停止，不启动子 agent。

父会话必须先产出**路径清单**和 **`git diff` 文本**（或按目录切好的 diff 片段），再按下面的机器检查落点跑变更包上的确定性扫描，然后才决定深度和是否启动子 agent。不要让每个子 agent 自己再跑一遍全库 `git diff`、自己发明扫描，或通读文件。

## 1.1 要求与机器检查

`AGENTS.md`、各轴 practice 和 [conventions.md](conventions.md) 里的条款是**要求**。有了 lint 或扫描器也不删、不改写成「以工具为准、不再写要求」。工具只负责证明某条要求在这次 diff 上有没有被违反。

能静态判定的检查**优先放进各包 lint**（该语言特有的扫描也一样，例如 React 的 React Doctor），不要留到 review 子 agent 再跑一遍。

**谁跑、产出在哪：**

1. 父会话按**项目机器检查落点**（仓库 `AGENTS.md`；没有该节时按各包 `package.json` 的 `lint` / `typecheck`）对变更涉及的包跑已列出的命令。
2. 子 agent 不自行选择工具、不重跑扫描，只读父会话贴上的退出码和摘要。
3. 本次会话已经跑过的同一命令复用产出，不要再跑。
4. 工具不是语言通用时：要求仍写在对应 practice（如 React 条款在 [react.md](../practice/react.md)）；**命令、适用范围和产出路径**写在项目机器检查落点，不要写在通用 practice 里冒充全语言可用。
5. 某个包没有对应工具：要求仍然有效。父会话按 diff 抽查，并在报告写明「该包无机器检查」。
6. lint / 扫描已能报的问题不写成 Finding，只在报告里留工具结果（命令、规则名、文件位置）。

变更路径超过 40 个文件，或新增+删除超过 1500 行，且用户没有指定 Story、目录或文件切片时：先问一次范围（按 Story / 目录切开，还是继续看全部）。未得到回答前不启动子 agent，也不自动升为全量六轴。用户确认看全部时，仍按第 3 节的深度选轴。

## 2. 确定 Spec

按顺序寻找：

1. 提交或 PR 引用的 issue。
2. 用户提供的 PRD、Story 或意图文件。
3. 与分支和改动匹配的 `docs/user_stories.md`、`docs/prd/`、`docs/testing/`。
4. 当前对话中的明确要求。

WIP 深度只需要 Story 与可观察验收；不要为了对齐而把画像、旅程和未改动的 PRD 章节整份读进子 agent。仍无法确定且有无 Spec 会改变结论时，询问用户。用户确认没有正式 Spec 后，以对话意图为准，并在报告中注明 Spec 仅来自当前对话。

## 3. 选择深度与评审轴

深度和适用轴见 [review-axes.md](review-axes.md)。不要默认六轴全开。

- **WIP（默认）**：未点名「全量」「六轴」「合并前」「准备提交」时，跑 **Design、Clean、Stack**；测试文件有变化时追加 **Testing**。最多四个子 agent。
- **全量**：用户点名上述词，或明确说这是合并前 / 交付评审时，再按 [review-axes.md](review-axes.md) 运行适用轴，并记录跳过原因。

同一轮并行启动的 `generalPurpose` 子 agent 不超过适用轴数量，每个子 agent 只处理一个轴。提示词只包含：

- 仓库路径、基线、差异范围、提交列表和**本轴相关**的变更路径（不要贴全库文件树）。
- 父会话已经准备好的 diff 片段，或该片段的文件路径；要求默认只根据 diff 下结论。
- Testing 轴额外提供变更测试文件的完整 `describe` / `it` 结构，以及相关测试层已有用例的标题清单。
- 本轴需要读取的项目规则与参考文档（只列本轴，不附其他轴的 practice）。
- Spec 来源；除 Spec 轴外，只提供理解改动所需的最少背景（Story ID、验收条目，不要整份 PRD）。
- [review-format.md](review-format.md) 的问题项要求。
- 下面的阅读规则和本轴模型（见第 3.1、3.2 节）。
- 无发现时说明检查范围。

子 agent 的结论是候选问题项（Finding）。主 agent 负责合并针对同一代码位置的重复问题，并判断最终编号和严重度。

### 3.1 阅读规则

子 agent **默认只读 diff 和父会话点名的路径**，不要为了写引用去 `Read` 整份源文件。

只有准备写下 **P0 或 P1** 时，才允许 `Read` 该文件中问题附近的局部（优先用行号窗口，不要整文件）。P2 / P3 用 diff 中的行号定位即可。

Testing 轴例外：可以读取变更测试文件全文，并检索相关测试目录中的 `describe` / `it` 标题，以判断重复覆盖、颗粒度和已删除逻辑；不要因此通读无关生产代码或整个测试树。

主 agent 聚合时：

- 只复核 **P0 / P1**：读取问题项给出的位置，确认当前文件仍是这样。
- 不要把各轴读过的文件再通读一遍。
- 不要为了写架构概览重新走一遍 `/lh understand` 式的全量阅读；WIP 报告不写 Architecture Brief。

### 3.2 子 agent 能力档

六轴不都使用同一档模型。按 [review-axes.md](review-axes.md) 的**意图**选档，不要写死某个产品型号：当前 agent 能用的模型因账号和会话而异。

- **Design、Clean**：判断档。优先与父会话同级，或已有模型里判断力最强的一档。
- **Stack、Spec、Testing、Conventions**：轻量档。优先用更快、更省的编码模型；没有单独的轻量档时，退回父会话模型。

启动子 agent 时，在当时可用的模型列表里选最接近该意图的一档，把**实际用的档**（判断 / 轻量）和运行时模型标识写进报告。用户点名某轴用哪一档时，以用户为准。

Conventions 在全量深度默认由**主 agent**根据 `git diff --name-status` 和仓库命名 / 目录 / 迁移规则检查，不启子 agent。仅当新文件很多、或日志 / 迁移约定有争议时，才启轻量档子 agent。

## 4. 聚合证据

1. 对 P0 / P1：确认引用的是当前文件真实内容，位置和标准可定位。P2 / P3 以子 agent 给出的 diff 位置为准，位置明显对不上时再读局部。
2. 同一问题跨轴时选择主轴，在卡片中注明相关轴。
3. 仅全量深度按 [understand.md](understand.md) 的读者模型写架构概览（Architecture Brief）。WIP 深度省略该节。
4. 将需要处理的问题项放入决策清单（Decision Board）。WIP 深度的决策清单只放 P0 / P1；P2 / P3 可留在各轴正文，不进清单。保留各轴原结论，不强行合并各评审轴之间不同的判断。
5. 使用 [review-format.md](review-format.md) 的结构写入 `docs/reviews/`。WIP 与全量的章节不同，见该文件。

## 完成条件

评审完成时：

- 基线、工作区范围、提交、变更路径和**评审深度**可复核。
- 每个适用轴都有问题项或“无发现”，每个跳过轴都有理由。
- 每条问题项都有真实代码位置、标准、具体影响和可执行下一步。
- 全量深度的架构概览能让未读过代码的人理解主要调用路径；WIP 深度不要求架构概览。
- 报告已写入文件，决策清单与进入清单的问题项编号一致。
- 用户收到报告路径、易懂的总体结论和关键行动摘要。

只有用户另行要求修复时，才修改被评审的生产代码。
