# 六轴评审

`/lh review` 基于固定的 Git 基线，对改动执行六轴评审并将证据写入报告。该命令判断改动是否需要修改，不代替用户修改代码。

开始前读取：

- [review-axes.md](review-axes.md)：六轴标准、范围和判断重点。
- [review-format.md](review-format.md)：问题项、代码位置和报告格式。
- 仓库 `AGENTS.md`：项目规则优先。

## 1. 固定范围

先确定用户要评审分支改动还是仅评审工作区。分支评审使用用户指定的提交、分支、标签或其他 Git 引用；未指定且仓库没有明确默认时，询问一次，常见默认是 `origin/main`。用户明确只看未提交改动时，以 `HEAD` 为参照，不纳入当前分支已有提交。

开始评审前完成以下检查：

1. `git rev-parse <base>` 能解析基线。
2. 采集 `git log <base>..HEAD --oneline`、差异统计和变更路径。
3. 分支评审默认包含 `<base>...HEAD` 的提交以及当前工作区已暂存、未暂存和未跟踪的文件；用户明确只看提交或只看工作区时按要求收窄。
4. 差异非空。基线无法解析或没有差异时在此停止，不启动子 agent。

## 2. 确定 Spec

按顺序寻找：

1. 提交或 PR 引用的 issue。
2. 用户提供的 PRD、Story 或意图文件。
3. 与分支和改动匹配的 `docs/user_stories.md`、`docs/prd/`、`docs/testing/`。
4. 当前对话中的明确要求。

仍无法确定且有无 Spec 会改变结论时，询问用户。用户确认没有正式 Spec 后，以对话意图为准，并在报告中注明 Spec 仅来自当前对话。

## 3. 选择评审轴

根据 [review-axes.md](review-axes.md) 运行适用轴并记录跳过原因。默认六轴为 Design、Clean、Conventions、Testing、Stack、Spec。

同一轮并行启动最多六个 `generalPurpose` 子 agent（subagent）。每个子 agent 只处理一个轴，提示词包含：

- 仓库路径、基线、差异范围、提交列表和变更路径。
- 本轴需要读取的项目规则与参考文档。
- Spec 来源；除 Spec 轴外，只提供理解改动所需的最少背景。
- [review-format.md](review-format.md) 的问题项要求。
- 要求引用前读取当前文件，报告具体位置、标准、影响和建议；无发现时说明检查范围。

子 agent 的结论是候选问题项（Finding）。主 agent 负责核对代码位置、合并针对同一代码位置的重复问题，并判断最终编号和严重度。

## 4. 聚合证据

1. 逐条确认问题项引用的是当前文件真实内容，位置和标准可定位。
2. 同一问题跨轴时选择主轴，在卡片中注明相关轴。
3. 按 [understand.md](understand.md) 的读者模型写架构概览（Architecture Brief），使尚未读过这批改动的人先理解用户路径、关键术语、调用顺序和分层。
4. 将需要处理的问题项放入决策清单（Decision Board），保留各轴原结论，不强行合并各评审轴之间不同的判断。
5. 使用 [review-format.md](review-format.md) 的结构写入 `docs/reviews/`。

## 完成条件

评审完成时：

- 基线、工作区范围、提交和变更路径可复核。
- 每个适用轴都有问题项或“无发现”，每个跳过轴都有理由。
- 每条问题项都有真实代码位置、标准、具体影响和可执行下一步。
- 架构概览能让未读过代码的人理解主要调用路径。
- 报告已写入文件，决策清单与问题项编号一致。
- 用户收到报告路径、易懂的总体结论和关键行动摘要。

只有用户另行要求修复时，才修改被评审的生产代码。
