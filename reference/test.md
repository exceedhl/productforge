# 自动化测试编写 (Automated Testing)

`/lh test`

用户说「写测设 / 测试设计」→ 写或改测设文档。用户说「补测试 / 写测试」→ 按测设写测试代码。只点命令：缺测设则先设计，已有测设则写代码。

核心原则和规范，与具体语言和框架无关。

> 若当前仓库有 `AGENTS.md`，其中的项目测试约定优先于本文件默认。本命令不依赖它才能开工。
>
> **上游**: 建议先完成 `/lh arch`。测试场景应对应 Backlog（`docs/user_stories.md`）与 `docs/prd/` 中对应 PRD 的验收标准。

---

## 交互式引导 (Interactive Discovery)

开始编写测试前，确认以下上下文：

1. **测试类型**: 需要写哪种测试？（按下面「测的是问题不是工具」分类，不要先选 Playwright / RTL）
2. **被测对象**: 测试哪个模块或功能？对应哪个 User Story？
3. **现有测试**: 项目中已有测试吗？用的什么框架？
4. **环境依赖**: 需要外部服务（数据库、API）吗？如何 mock 或 seed？
5. **覆盖目标**: 有具体的覆盖率要求吗？重点覆盖哪些风险区域？

---

## 工作流

### 新 Story / 新功能

1. 读取 PRD AC，写出测试设计（场景、接缝/长路径、Mock 策略）。
2. 编写功能代码。开发过程中可以集中推进实现，不要求每个小改动都立即写测试或全量回归。
3. 功能代码完成后，集中补齐或更新自动化测试，按改动范围回归。
4. 交付前确认 PRD、测试设计文档、测试代码三者一致。

### Bugfix

1. 先写能复现问题的失败测试；必要时在设计文档补一条待覆盖场景。
2. 修改生产代码让复现测试通过。
3. 回归同层相关用例。
4. 若 Mock 边界或覆盖意图变化，更新设计文档。

### 重构 / 行为不变

不强制新增用例。若移动测试文件、改变 Mock 边界或暴露覆盖缺口，同步设计文档。不要长期双轨维护同一风险的两套用例。

---

## 测的是问题，不是工具

没有独立的「E2E」类型。Playwright、RTL、HTTP 客户端、WebSocket 客户端都是**执行手段**，不是层。

按测试回答的问题分类：

| 问的是 | 层 |
|---|---|
| 单模块规则（SQL、状态机、纯函数） | Unit |
| 单入口、单能力能不能用 | 单能力（Functional / Component） |
| 一条短协作接缝的副作用对不对 | 短接缝（Integration） |
| 跨域、多步之后终态是否一致 | 长路径（Integration） |

**选型口诀：** mock 掉下游之后，要抓的 bug 还能复现吗？能 → Unit 或单能力；不能 → 短接缝或长路径，下游必须真实。

**对外边界默认走集成：** 客户端真实碰到的 HTTP / WS / 同类传输，带着协作链和副作用测。Unit / 单能力只补集成盖不住的分支（迁移、纯校验、还没有接缝的快针）。

同风险不重复测：短接缝已覆盖的规则，不要再写一条只验同一件事的单能力或长路径。

## 一、文件组织与命名

下面是**无项目细则时的回退树**。仓库若已有测试目录、层名或文件后缀约定，以项目约定为准，不要另开一套。

```
tests/
├── unit/            # 隔离的函数/模块级测试
├── integration/     # 接缝与长路径
├── functional/      # 可选：单能力
├── performance/     # 负载、响应时间、吞吐量
└── fixtures/        # 共享的测试数据、setup 脚本
```

项目层名（如 Seam / Journey）映射到上表的「短接缝 / 长路径」，不必改成这套英文目录名。

### 命名原则
- **文件名反映被测对象**
- **场景文件反映业务故事**
- **Fixture 职责清晰**: 认证 setup、数据 seeding、常量定义分开

---

## 二、场景覆盖原则

### Happy Path + Sad Path 并行覆盖

每个测试场景**必须**同时包含正常流程和异常流程。

### 边界条件清单

| 数据类型 | 检查项 |
|---|---|
| **字符串** | 空串、超长、特殊字符、Unicode、注入向量 |
| **数字** | 零、负数、极大/极小值、浮点精度、NaN |
| **集合** | 空集、单元素、大量元素、重复、嵌套 |
| **时间** | 跨时区、夏令时、闰年、格式不一致 |
| **状态** | 初始、中间、终态、并发修改、幂等性 |

### AAA 结构
1. **Arrange**: 准备环境和数据
2. **Act**: 执行被测行为
3. **Assert**: 验证具体预期值（拒绝模糊断言）

每个用例只回答一个问题。长路径允许多步，但只讲一个用户故事。

## 三、测试数据设计 (Golden Dataset)

### 设计原则
- **固定标识符**: 使用常量 UUID，确保可重复和可调试
- **覆盖所有分类**: 每个业务分类至少一条测试数据
- **时间跨度**: 包含不同时间段的数据

### 语义陷阱 (Semantic Traps)

| 陷阱类型 | 说明 | 示例 |
|---|---|---|
| **一词多义** | 相同词不同语境 | "Bank" → 银行 vs 河岸 |
| **实体混淆** | 同名不同领域 | "Apple" → 科技公司 vs 水果 |
| **同义替换** | 不同措辞同一概念 | "心肌梗死" vs "心脏病发作" |
| **精确匹配干扰** | 子串相同语义不同 | 标题包含相同关键词但主题完全不同 |
| **噪声数据** | 与目标无关 | 验证系统不会误匹配 |

### Seeding 规范
- **幂等性**: 使用 upsert，可安全重复运行
- **独立性**: 测试数据与生产数据完全隔离；测试不得读写生产数据目录
- **最小化**: 只创建当前场景必需的数据

## 四、Web 应用测试

### 选择器优先级（从高到低）
1. **专用测试属性** (`data-id`, `data-testid`) — 最稳定
2. **语义角色** (`getByRole`) — 兼顾无障碍性
3. **文本内容** (`getByText`) — 适用于稳定文案
4. **CSS 类名 / XPath** — 避免使用

### 测试属性命名
- 语义化连字符: `data-id="topic-link-AI"`, `data-id="star-button"`
- 列表项加前缀: `data-id="briefing-item-{id}"`
- 面板用角色: `data-id="event-detail-panel"`

### 等待策略
- 拒绝固定等待 (`sleep`/`waitForTimeout`)
- 使用条件等待（元素可见、请求完成、状态变更）
- 设置有业务含义的合理超时

### 行为，不是实现
- 测用户能看见或能完成的行为，不测内部 state / 样式类名。
- 网络在系统边界 mock，不在组件树中间拦自己人。
- 每个交互点至少一条正常 + 一条代表失败（校验、空态、权限、超时）。

前端同样按问题分层：钩子/工具单测、单组件、短协作、跨页终态。RTL / Playwright 只是手段。

## 五、Mock

1. **只 mock 测试焦点之外的依赖**。
2. **测行为，不测实现** — 断言持久化、HTTP body、error code、可见 UI，而不是内部调用次数。
3. 只 mock **无法控制或代价过高**的边界（外部 HTTP、LLM、worker）；不要 mock 本测试要证明的内部协作。

### 写路径要断言持久化终态

**写路径**指 Act 会写入、更新或删除数据的测试（创建资源、刷新落盘、迁移、删除）。

短接缝 / 长路径不能只断言响应（HTTP 200、返回 body、一次函数没抛错）。还要断言**事后仍能读到的副作用**：

- 数据库行是否在、状态字段是否正确
- 落盘文件 / artifact / 对象存储是否与读回 API 一致
- 失败或回滚后，旧数据仍可读、没有半写入

没有持久化的纯计算接口，只断言返回值即可。细节分支（某字段校验失败）仍由 Unit 覆盖，不必每条都走集成。

## 六、迁移测试

迁移（schema 升级、数据改写、文件搬迁）属**单能力**，验证升级逻辑本身。

| 策略 | 说明 |
|---|---|
| **主路径：相邻版本** | 每个用例验证 **N → N+1** 一步（schema 或数据），失败时能定位版本 |
| **辅路径：长链路 smoke** | 少量用例覆盖基线 → 最新版本，不按每个中间步重复断言 |
| **代码迁移隔离** | 应用层 migrator（大 JSON、文件搬迁）与 DDL 不要塞进同一个用例 |
| **异步** | 入口若是 async，setup / `beforeEach` 必须 `await`，避免库版本未到位 |
| **失败语义** | migrator 抛错时版本号**不应**前进；成功后才断言目标版本 |

不要 mock 被测迁移逻辑。测试库与生产数据隔离。

## 七、昂贵依赖与 LLM

是否调用真实 LLM **不是**分层依据。按被测风险选：

```text
本用例是否依赖模型输出质量 / Prompt / 自愈？
├─ NO  → stub 模型（以及沙箱等昂贵依赖）
└─ YES → 真实调用；无密钥则逐条 skip，不让整套失败
```

- 测状态机、持久化终态、错误映射：stub。
- 测 Prompt / 生成质量 / 自愈：真实调用；无密钥 skip **单条**，禁止整 suite skip，也不为此拆第二套 runner / tag。
- 已有真实调用覆盖同一风险 → 删除 stub 的同类长路径，勿双轨。
- 其它无法控制或代价过高的边界（外部 HTTP、worker）同样：焦点之外才 stub。

## 八、测试设计文档

测设是给人读的活文档，和运行结果分开。场景描述遵守 skill 通用 [llm-output.md](llm-output.md)：先写用户在哪个页面做什么，再写断言什么；不要只写函数名。

- 覆盖什么风险？不覆盖什么？
- 正常路径、异常路径和关键边界
- 哪些依赖真实，哪些 mock，为什么？
- 长路径覆盖哪些 Story / AC？
- 还有哪些待补齐场景？

**不要**把测试通过/失败回写进设计文档。

推荐结构：覆盖意图、场景列表、Mock 与测试数据策略、已知缺口；长路径文档加「对应 User Stories」。

默认落在 `docs/testing/`。

---

## 九、文档同步

- **新增功能** → 必须同时编写对应测试
- **修改功能** → 检查并更新受影响的测试
- **修复 Bug** → 先补复现测试，再修复代码（回归防护）
- **新发现边界用例** → 加入 Golden Dataset
