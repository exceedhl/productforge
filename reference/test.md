# 测试

`/pf test` 按风险设计测试，或根据已有测试设计补写测试代码。

先读取仓库测试指南；没有项目规则时使用 [testing-model.md](testing-model.md)。

## 选择任务

- 用户要求测试设计、场景或覆盖策略：创建或更新 `docs/testing/` 中的测试设计。
- 用户要求补测试或写测试：读取相关 Story、PRD、测试设计和现有测试后修改测试代码。
- 用户只输入 `/pf test`：缺测试设计时先设计；已有设计且实现完成时补测试。不确定且两种产出差异较大时只问一个问题。

工具和框架由仓库现状决定，不根据 Playwright、React Testing Library 或 HTTP 客户端等工具名称决定测试层。

## 1. 确定风险

从用户行为、PRD 验收标准、缺陷症状或重构范围中列出本次需要验证的行为和可能失败的情况。只询问仓库和对话无法确定、且会改变测试方案的信息，例如外部环境是否可用。

每项风险说明：

- 用户或调用方从哪个公共入口触发行为。
- 成功、有代表性的失败场景和关键边界条件分别是什么。
- 最终应观察返回值、可见 UI、协议响应还是持久化状态。
- 哪些内容明确不在本次覆盖范围。

## 2. 选择测试层

按仓库测试指南选择能够暴露当前风险的最小测试层；没有项目规则时使用 [testing-model.md](testing-model.md)。

优先复用已有公共接口和测试基础设施。如果现有公共接口无法验证真实行为，调整模块职责或增加依赖替换能力都会改变业务代码架构，必须先确认该调整属于当前范围。

## 3. 设计依赖与数据

明确哪些依赖使用真实实现，哪些使用 Mock，以及每种选择分别覆盖哪些风险。测试数据保持最小、确定、幂等并与生产隔离。

涉及写入、更新或删除的测试必须验证操作完成后仍可读取的状态。外部服务、LLM 和其他昂贵依赖根据本测试要验证的行为决定是否真实调用。

## 4. 执行

### 新功能

1. 将 PRD 验收标准映射为测试场景。
2. 写测试设计，明确风险、测试层、依赖和数据。
3. 功能实现完成后补齐自动化测试。
4. 运行受影响测试文件中的用例、相关测试和交付检查。

### 缺陷修复

1. 先写能复现用户症状的失败测试。
2. 确认测试失败原因就是报告的问题。
3. 修改生产代码，使测试通过。
4. 回归同一测试层的相关用例，并更新受影响的测试设计。

### 行为不变的重构

使用现有测试证明行为保持不变。只有现有测试确实无法覆盖某项行为、测试文件或测试层发生变化，或依赖被 Mock 的范围发生变化时，才修改测试和设计文档。

## 测试设计文档

测试设计是给人阅读的风险说明，不记录某次运行结果。推荐结构：

1. 覆盖意图与范围。
2. 场景及对应 Story / 验收标准。
3. 测试层与公共入口。
4. 真实依赖、Mock 和测试数据。
5. 已知缺口及接受理由。

场景先描述用户或调用方做什么，再写观察什么；不要只列函数名。

## 评审和维护现有用例

用例集合按当前风险和业务分支划分，并满足 MECE：

- 两条 `it` 验证相同的触发条件、失败原因和可观察结果，属于重复；只更换 fixture 值不构成新风险。
- 主要正常路径、代表性异常路径和关键边界应有覆盖，但不机械枚举所有输入组合。
- 同一风险只在最合适的测试层验证一次，上层不逐项复测底层规则。

`describe` 可以按被测对象、能力或场景组织，以最能表达测试意图的方式为准，不强制按生产代码符号拆分。同一 `describe` 下的 `it` 应处于同一抽象层级。每个 `it` 只回答一个问题；共同证明一个结果的多个字段断言留在一条用例中，不按字段拆成碎片。Journey 可以包含多步，但只验证一个用户故事的最终结果。

## 断言当前契约

测试要证明「现在必须这样」，不是「以前不是那样」。改功能时顺手加的否定断言属于改动期的脚手架，行为稳定后就该拆掉，否则下一个人读不出当前契约，还会被旧名字误导。

判定标准：把这条断言单独给没读过改动历史的人，他能否从中看出当前的正确行为。看不出就是历史包袱。

**要写的**

- 正常路径：当前输入下，输出必须包含什么值、写入什么状态、调用什么下游。
- 异常路径：缺参、未授权、未配置、下游失败时的错误码、提示，以及副作用没有发生。

**不要写**：按断言锚在什么判断，三类都要改锚点。

| 锚在 | 典型写法 | 为什么脆 | 改成锚在 |
|---|---|---|---|
| 旧值、旧名字 | 输出不含旧字段 / 旧文案 / 旧占位符 / 旧依赖名 | 旧名字彻底消失后断言恒真，读者仍不知道现在该是什么 | 当前值：断言现在的字段、文案、占位符确实出现 |
| 实现载体的文本 | grep 源码断言符号已删除；断言文件不存在、某处不再 import、快照逐字等于旧文案 | 约束的是承载方式而非行为，重命名、移动文件、换模板就失效或误报 | 可观察行为：入口返回值、持久化终态、对外响应 |
| 「缺了什么」 | 一串旧字段应为 undefined | 只说不该有什么，没说该有什么 | 完整集合：当前字段名或 id 列表整份 `toEqual`，旧字段自然被排除 |

属于别的模块或别的 Story 契约的断言（平台差异、旧版体积对比），放回负责那条逻辑的用例，不要因为顺路留在这里。

唯一该保留的否定断言：回退会破坏协议、泄露数据或造成成本事故的那一条。例如敏感字段不得出现在响应里、内部标识不得进入对外目录、某一层不得挂载另一层的能力。这类断言约束的是永远不允许出现的行为，与改动历史无关；标题里要写清为什么禁止。

## 完成条件

- 每项纳入范围的风险都有对应测试或明确接受的缺口。
- 所选测试层能够暴露当前风险，没有重复验证同一风险。
- Mock 没有替代本测试要验证的内部协作；涉及写入、更新或删除的测试验证了持久化后的最终状态。
- 缺陷修复的复现测试在修复前失败、修复后通过。
- 断言证明当前契约，而不是「不再等于某个旧值」。
- Story、PRD、测试设计和测试代码保持一致。
- 已运行仓库规定的 lint、typecheck、test、build；无法执行的检查项及剩余风险已说明。
